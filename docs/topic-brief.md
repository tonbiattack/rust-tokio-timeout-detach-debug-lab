# 題材企画: Tokioのタイムアウト後にワーカーが状態を更新する

## 対象

| 項目 | 内容 |
| --- | --- |
| 対象言語 | Rust 1.75.0 |
| 対象読者 | `tokio::spawn`、`async`/`await`、`tokio::time::timeout`を使ったことがあり、実行時の不具合をテストで切り分けたい開発者 |
| 難易度プロファイル | 実践・上級 |
| 選定理由 | 呼び出し元の期限切れと、バックグラウンドタスクの実行継続という一見矛盾する観測を、ログ・コードリーディング・デバッガー・テストで結び付けて切り分けるため |
| 実行基盤 | Cargo、組み込みテスト、Tokio 1.36以上 |
| フレームワーク非依存性 | Webフレームワーク、DB、外部サービスを使わず、Tokioランタイムとメモリ上の状態だけで再現する |

## 学習する契約

> ワーカーの完了を`timeout`で待ち、期限切れになった場合、呼び出し元は`DeadlineExceeded`を返すだけでなく、ワーカーによる後続の状態更新を許してはならない。バグ状態では`DeadlineExceeded`を返した後も、ワーカーが`Completed`へ更新する。

### 対象の直接原因

`tokio::time::timeout`が待機対象の`JoinHandle`を期限切れでドロップし、`JoinHandle`のドロップがタスクを中断せずデタッチするという、二つのAPI契約の相互作用です。

### 対象外

HTTPタイムアウト、分散トランザクション、データベースのロールバック、`spawn_blocking`の停止保証、親子タスク全体の構造化並行性は扱いません。

## 再現設計

| 要素 | 決定 |
| --- | --- |
| 公開境界 | `run_job_with_deadline`関数 |
| 入力・初期状態 | `Pending`状態、起動を同期する`Barrier`、ワーカーを解放する`oneshot`チャネル |
| Redの観測 | 期限切れの戻り値を確認後、解放メッセージが受理され、最終状態が`Completed`になるため契約テストが失敗する |
| 最終観測 | 戻り値、チャネル受理可否、共有状態を別々に確認する |
| 決定性 | `Barrier`によりワーカーが待機状態へ入った後で期限を待つ。任意の`sleep`で実行順を制御しない |
| 固定状態の検証コマンド | `cargo test -- --nocapture` |
| バグ状態の確認コマンド | `cargo test deadline_expiry_must_not_allow_a_late_state_change -- --nocapture` |

## 仮説

| 仮説 | どう検証または除外するか |
| --- | --- |
| `timeout`が期限切れ後もワーカーを実行している | 期限切れのログ後に制御メッセージが受理され、`Completed`へ更新されるログと最終状態を確認する |
| ワーカーが期限切れより前に状態を更新している | ワーカーを`oneshot`受信で停止し、期限切れ後にだけ解放することで除外する |
| 共有状態のロック取得が遅延し、見かけ上古い状態を読んでいる | 完了通知を待ってからロックを読み、最終状態を確認することで除外する |
